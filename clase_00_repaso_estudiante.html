2 EL MODELO: openai/gpt-oss-120b

Ese nombre no es al azar. Tocá cada parte para ver qué significa:

openai/gpt-oss-120b
🔄 Los modelos se dan de baja: esto pasó de verdad, hace unos días Hasta hace poco este taller usaba llama-3.3-70b-versatile. Groq anunció que deja de funcionar el 16 de agosto: después de esa fecha, cualquier programa que lo pida recibe un error. Por eso migramos a openai/gpt-oss-120b.

Esto es parte normal del oficio: los modelos se actualizan y se retiran, y quien programa con IA tiene que estar atento. La buena noticia es que el cambio fue una línea: como el resto del código no depende del modelo, se reemplaza el nombre y todo lo demás sigue igual. Cuando programás bien, cambiar de motor no te obliga a rehacer el auto.
⚠️ Qué hace un LLM (y qué NO hace) Un modelo de lenguaje predice el texto más probable, pedacito por pedacito, a partir de lo que aprendió al entrenarse. Por sí solo, no verifica contra ninguna fuente: no está leyendo internet ni consultando una base de datos con la verdad mientras te responde. Cuando le falta un dato, igual completa con algo verosímil: eso es una alucinación, y no es un error del programa — es cómo funciona.

Ojo: hay asistentes (como algunos chatbots que usás) que sí pueden buscar en internet — pero eso es una herramienta extra que les conectaron aparte. El modelo pelado, como el que usan ustedes por la API, no lo hace: responde solo con lo que tiene adentro.
Por eso el proyecto nuevo se llama Extractor y no "Adivinador" Vas a pedirle que saque datos que están escritos en el texto, y después vas a verificar que no haya inventado nada. Ese control es una de las partes que se evalúan.

3 JSON: EL IDIOMA DEL VIAJE

Tu Colab habla Python; el servidor no sabe Python. Para entenderse usan un formato neutro que entienden los dos: JSON. Todo lo que va y lo que viene tiene esta forma.

➡️ Lo que SALE de tu programa (el payload):

{ "model": "openai/gpt-oss-120b", <- qué modelo querés "temperature": 0.7, <- cuánto puede variar "messages": [ <- TODA la conversación {"role": "system", "content": "Sos el Narrador..."}, {"role": "user", "content": "abro la puerta"}, {"role": "assistant", "content": "La puerta cruje..."} ] }

⬅️ Lo que VUELVE del servidor:

{ "choices": [ <-- 1) ["choices"] : es una LISTA { <-- 2) [0] : el primer elemento "message": { <-- 3) ["message"] "role": "assistant", "content": "Detrás de la puerta hay..." <-- 4) ["content"] } } ], "usage": {"total_tokens": 512} <- cuánto consumiste }

Seguí los cuatro números del dibujo: son exactamente los corchetes de la línea que ya conocés, en el mismo orden.

respuesta.json()["choices"][0]["message"]["content"] 1 2 3 4

Ojo con el [0]: no está escrito en el JSON. Aparece porque después de "choices" hay un corchete [, y eso quiere decir lista. Los elementos de una lista no tienen nombre: se piden por su número de posición, y el primero es el 0.

Por eso hay que "cavar" hasta el texto El servidor no devuelve la frase pelada: devuelve una caja con cajas adentro. Cada corchete abre una:

respuesta.json() → todo el JSON
["choices"] → la lista de respuestas
[0] → la primera (y única: ver la nota de abajo)
["message"] → el mensaje
["content"] → el texto que buscabas
🤔 ¿Por qué siempre [0]? ¿Alguna vez es [1]? Con Groq, nunca. Esa lista existe porque la API está preparada para devolver varias respuestas distintas a la misma pregunta: si pudieras pedir tres, tendrías [0], [1] y [2] para comparar y elegir. Pero Groq solo admite una por pedido, así que la lista siempre tiene un elemento y el [0] nunca cambia.

No es que el número sea de adorno. En tus propias listas va a cambiar todo el tiempo: cuando tu proyecto procese los diez archivos del corpus, resultados[0] será el primero, resultados[1] el segundo, y así. Acá queda fijo solo porque la respuesta viene de a una.

🏆 Completaste los seis Fijate el patrón: cada corchete abre una caja. Si el valor es otro diccionario, entrás con otra clave. Si es una lista, entrás con un número de posición. Eso es todo: no hay más misterio.

Y fijate el contraste entre el caso 1 y el caso 4: en la respuesta de la IA el [0] es siempre 0, porque Groq devuelve una sola. En una lista tuya, el número cambia según cuál quieras.
💡 Por qué esto importa para el proyecto El Extractor que vamos a construir hace exactamente esto, pero al revés: le pide a la IA que arme un JSON con los campos que vos elegís, y después tu programa lo recorre para sacar cada dato. 5 DISECCIÓN DE TUS BLOQUES B2 Y B3

Estas son las líneas que venís escribiendo desde la Clase 6. Ahora las leemos entendiendo qué hace cada una:

# ===== B2 — LA CONFIGURACIÓN ===== API_KEY = "gsk_TU_CLAVE" # ^ Tu credencial. Identifica QUIÉN hace el pedido. No se comparte nunca. URL = "https://api.groq.com/openai/v1/chat/completions" # ^ La dirección exacta del backend: el "endpoint". # Es la puerta del servidor a la que le tocás el timbre. headers = {"Authorization": f"Bearer {API_KEY}", "Content-Type": "application/json"} # ^ Los datos del sobre: QUIÉN sos (Authorization) # y EN QUÉ IDIOMA le hablás (Content-Type: json). # ===== B3 — LA FUNCIÓN QUE HACE EL VIAJE ===== def consultar_ia(mensajes, nivel_creatividad): payload = {"model": "openai/gpt-oss-120b", "temperature": nivel_creatividad, "messages": mensajes} # ^ EL PEDIDO en JSON: qué modelo, cuánta variación, # y toda la conversación hasta ahora. try: respuesta = requests.post(URL, headers=headers, json=payload) # ^ EL VIAJE DE IDA. post = "te mando datos". # Acá tu programa se queda esperando la respuesta. return respuesta.json()["choices"][0]["message"]["content"] # ^ LA VUELTA, desarmada caja por caja hasta llegar al texto. except Exception as e: return f"Error: {e}" # ^ Si se cae internet o la clave está mal, avisa en vez de romperse.
Estas líneas son TODA la conexión con la inteligencia artificial El resto de tu RPG (el bucle, los comandos, el diccionario del jugador) es Python común. La IA entra por acá. Y en el proyecto nuevo este bloque se reusa casi sin tocar.

6 LOS ROLES Y EL CONTEXTO

Cada mensaje del historial lleva un rol. Asigná el que corresponde a cada uno:

"Sos el Narrador de una aventura de terror. Nunca rompas el personaje."
"abro la puerta con cuidado"
"La puerta cruje. Adentro hay una escalera que baja hacia la oscuridad."
🧠 La memoria la ponés vos, no el servidor El servidor no guarda nada entre un pedido y el siguiente: se dice que la API es sin estado. La conversación existe solo porque tu programa la va acumulando en historial y la manda entera cada vez. Si no la mandás, el modelo arranca de cero como si nunca hubieran hablado.

🌡️ La temperatura va de 0 a 2 (si no la ponés, la API usa 1). ¿Qué valor le pondrías a cada tarea?

Sacar el nombre del cliente de un pedido, siempre igual
Narrar una aventura distinta en cada partida
🔢 Y los tokens El modelo parte el texto en pedacitos (tokens) y predice el siguiente. Hay un límite por pedido: si el historial crece mucho, no entra.

8 PREPARACIÓN — ¿QUÉ SE PUEDE EXTRAER?

Esta es la primera decisión del proyecto, y la que más lo condiciona: elegir qué datos se le piden a la IA. Practiquemos el criterio.

La regla Un campo sirve si el dato está escrito en el texto. No sirve si hay que interpretarlo, deducirlo o suponerlo — ahí es donde la IA empieza a inventar.

★ DESAFÍO OPCIONAL — EL CRONISTA

Para el que quiera ir más allá. Es el puente exacto entre el RPG que hiciste y el proyecto que viene: tu juego va a extraer los datos de su propia partida.

La consigna Al final de la partida (cuando el jugador escribe salir), tu programa le pide a la IA que lea todo el historial y devuelva en JSON: el nombre del héroe, los lugares que visitó, los objetos que consiguió y cómo terminó la aventura.

🤔 Dos preguntas para pensar mientras lo hacés
  • ¿Qué temperatura conviene? No estás pidiendo que narre: estás pidiendo datos. Probá con la que venías usando y después con una bien baja, y compará.
  • ¿La IA inventa algo? Revisá la crónica contra lo que realmente pasó en tu partida. ¿Aparece algún objeto que nunca conseguiste? Ese es el problema central del proyecto que arranca ahora.
